# Agent Goal 生命周期与可调试流式问答设计

## 背景与目标

当前聊天接口已经支持 SSE（服务器推送事件）逐段输出，但请求仍被视为一次不可控制的同步执行：前端只有一个全局 `loading` 状态，后端 Agent（智能代理）使用一次性 `agent_graph.invoke()`，检索轨迹只记录命中的数量。因此用户无法暂停任务、恢复任务、停止任务或在上一条回答未结束时继续提问，也无法从工作过程中判断 RAG（检索增强生成）到底检索了多少内容。

本设计把每次用户提问建模为一个持久化 Agent Run（执行任务），提供接近 Codex Goal（目标）的生命周期控制：暂停后不再自动继续，恢复时从最近的安全边界继续；停止、超时和错误成为明确的终态。前端可以同时展示多个任务，后端仍保证同一会话的持久化顺序。

目标：

- 支持 `运行中`、`暂停请求中`、`已暂停`、`已完成`、`已停止`、`已超时`、`失败` 状态。
- 暂停只在模型调用或工具调用结束后的安全边界生效，不尝试冻结第三方模型的半个 token（文本片段）。
- 恢复同一 Run 时不重复扣访客额度；重试会创建新 Run，并按一次新的 AI 请求计费。
- 用户可以在旧 Run 未完成时提交新问题；每条问题、回答、错误和控制按钮通过 `run_id`（执行标识）严格对应。
- 工作过程展示安全的检索调试元数据，包括 `top_k`、距离阈值、返回数量、排名、相似度和距离，不展示隐藏思维链、完整工具参数或未过滤文档正文。

## 非目标

- 不实现第三方模型生成中途的精确 token 级断点恢复；模型流一旦被主动停止，恢复属于从已保存安全边界继续，而不是从网络连接中间续播。
- 不把完整检索块、模型隐藏思维链、API Key（接口密钥）或工具参数写入前端轨迹。
- 不引入 PostgreSQL、消息队列或新的外部任务平台；持久化状态继续使用 SQLite（轻量关系型数据库）。

## 核心生命周期

```text
queued -> running -> pause_requested -> paused -> running -> completed
                    |                  |
                    +-> stopped        +-> stopped
                    +-> timed_out
                    +-> failed
```

- `queued`：请求已接受，等待同一会话的前一个 Run 释放会话锁。
- `running`：正在执行模型、工具或生成文本。
- `pause_requested`：用户发出暂停请求；当前安全步骤结束后进入 `paused`。
- `paused`：保存了可恢复的 Agent 状态，不会自动继续；用户点击继续才恢复。
- `completed`：完整回答和安全轨迹已经持久化。
- `stopped`：用户主动关闭，回滚未完成的用户轮次，不保存半截助手回答。
- `timed_out`：超过 Run 总时限，回滚未完成轮次并保留安全错误轨迹。
- `failed`：模型、工具或系统错误；保留可重试的用户问题信息，但不把内部异常返回给浏览器。

暂停的语义对齐 Codex Goal：它控制“是否自动进入下一步/下一轮”，而不是隐藏已经产生的文本。暂停在安全边界生效；恢复读取同一 Run 的 checkpoint（检查点）并继续工作。

## 后端设计

### 持久化任务状态

在现有 SQLite 数据库中增加 `agent_tasks` 表，字段包括：

- `run_id`：32 位随机标识，主键。
- `conversation_id`、`owner_id`：资源归属，所有读取和控制都必须同时校验。
- `user_message_id`：未完成轮次的用户消息引用。
- `status`：上述生命周期枚举。
- `checkpoint_json`：最近安全边界的 Agent 状态；只保存可恢复消息、工具使用记录、步骤和检索元数据，不保存密钥。
- `answer_prefix`：已经安全产生的回答前缀，仅用于恢复或错误展示，不直接作为最终助手消息保存。
- `error_code`、`error_message`：稳定的安全错误分类和用户可见提示。
- `quota_reserved`：表示访客额度是否已经预占，恢复时禁止再次预占。
- `created_at`、`updated_at`、`completed_at`：生命周期时间。

任务状态更新必须是带当前状态条件的事务更新，避免“暂停”和“完成”并发到达时互相覆盖。Run 控制接口必须检查 `owner_id`，不能把 `run_id` 当成授权凭证。

### Agent 安全边界与恢复

将现有 Agent Loop 拆成可重复调用的单步执行：每次模型调用、工具调用和最终回答判断完成后保存 checkpoint。下一步执行前检查：

1. `cancel_event` 是否已设置；是则进入 `stopped`。
2. 是否已超过 `AGENT_RUN_TIMEOUT_SECONDS`；是则进入 `timed_out`。
3. 是否收到暂停请求；是则保存当前状态并进入 `paused`。

恢复时从 checkpoint 重建 LangGraph（语言模型工作流）状态，不重新保存重复的用户消息、不重复预占访客额度。对同一 `conversation_id` 仍使用现有会话锁，保证数据库里的用户问题和助手回答顺序不交叉；前端不需要等待上一条流结束即可提交下一条，后端会将其置于会话队列中。

### SSE 事件协议

保留现有 `/api/agent/chat/stream`，新增 Run 控制接口：

- `POST /api/agent/chat/stream`：创建 Run，首先发送 `run` 事件。
- `POST /api/agent/runs/{run_id}/pause`：请求暂停，返回 `pause_requested`。
- `POST /api/agent/runs/{run_id}/resume`：从 checkpoint 继续，并返回同一套 SSE 事件。
- `POST /api/agent/runs/{run_id}/cancel`：主动停止并释放资源。
- `GET /api/agent/runs/{run_id}`：读取当前身份可见的状态。
- `GET /api/agent/runs?conversation_id=...`：刷新页面时恢复当前会话的活动和暂停任务。

事件类型：

- `run`：`run_id`、`conversation_id`、当前状态。
- `status`：`queued`、`retrieving`、`generating`、`pause_requested`、`paused` 等公开阶段。
- `token`：仅包含回答文本片段。
- `trace`：安全的步骤、工具和检索调试元数据。
- `paused`、`done`、`cancelled`、`timeout`、`error`：终态或可操作状态及稳定提示。

断开浏览器连接只停止发送，不自动把任务当成完成；只有主动取消接口或服务端检测到取消信号时才进入 `stopped`。这样刷新页面仍可以读取任务状态并决定恢复或关闭。

### 检索调试数据

新增 `RAG_TOP_K` 配置，默认值为 `5`，限制在 `1..20`；继续使用 `RAG_MAX_COSINE_DISTANCE`，并将实际值写入安全轨迹。知识库检索返回：

```json
{
  "top_k": 5,
  "max_distance": 0.45,
  "returned": 3,
  "matches": [
    {"rank": 1, "similarity": 0.91, "distance": 0.09},
    {"rank": 2, "similarity": 0.84, "distance": 0.16}
  ]
}
```

轨迹只保存数量和数值元数据，不保存完整 chunk 正文；前端在“查看工作过程”中显示检索阶段、Top K、阈值、返回数量和每个结果的排名。RAG 文档仍按不可信数据处理，不能执行其中的指令。

## 前端设计

- 用 `Map<run_id, RunView>` 管理并发任务，不再使用单一 `loading` 布尔值。
- 每个用户问题和助手占位回答都有稳定的 `run_id`，事件只更新对应卡片，禁止通过“消息数组最后一项”更新。
- 输入框在存在活动 Run 时仍可提交新问题；访客额度耗尽或身份未加载时才禁用。
- 活动回答显示“暂停”“停止”；暂停后显示“继续”，错误和超时显示“重试”。
- 重试创建新的 Run，并保留原失败卡片用于比较；恢复使用原 `run_id`。
- 页面刷新调用 Run 列表接口，恢复 `queued/running/paused` 的状态；无法恢复的连接只重新订阅，不重复创建请求。
- 轨迹面板增加状态转换、总耗时、模型耗时、工具耗时和 RAG 检索详情；不展示内部异常堆栈。

## 错误、超时和额度规则

- 后端模型调用继续使用现有模型超时；新增 Run 总超时，默认 `120` 秒，可由环境变量配置并限制范围。
- 超时和主动停止都会设置取消信号，阻止下一次模型或工具调用，并回滚未完成用户轮次。
- 模型鉴权、额度、工具和检索错误转换为稳定错误码；日志保留类型和 `run_id`，浏览器只收到可操作提示。
- 创建 Run 时访客额度只预占一次；暂停、恢复和网络重连不重复扣次；重试是新 Run，重新执行额度检查。
- SSE 连接断开不等同于用户主动停止，避免用户刷新页面时任务继续被误删。

## 安全边界

- 每个 Run 的控制接口检查当前身份、会话所有权和 `owner_id`。
- checkpoint、错误和轨迹禁止保存 `.env`、API Key、完整模型响应和隐藏思维链。
- 工具输出、检索文档和 MCP（模型上下文协议）结果一律当作不可信数据。
- 任务状态转换使用白名单枚举和参数化 SQL（结构化查询语言）。
- 前端展示的检索调试字段只来自后端生成的数值元数据，不能接受浏览器提交的 `top_k` 越权扩大查询范围。

## 验收标准

1. 用户在回答生成中点击暂停，当前安全步骤结束后状态变为 `paused`，不会自动继续；点击继续后同一 `run_id` 恢复。
2. 用户点击停止后任务进入 `stopped`，不保存半截助手消息，后续可以提交新问题。
3. 一个回答未结束时提交第二个问题，两个问题的 token、按钮、状态和最终回答不串线；同一会话持久化顺序正确。
4. 模型失败、检索失败、超时和 SSE 断开分别有可测试的状态和安全提示；重试不会复用旧 Run 的完成状态。
5. 访客恢复暂停任务不重复扣额度，重试按新请求扣额度，并继续遵守每日和 IP 限制。
6. 工作过程可以看到 `top_k=5`、距离阈值、返回数量、排名、相似度和距离；不出现 chunk 正文、工具参数、API Key 或隐藏思维链。
7. 后端测试、前端测试、ESLint（代码规范检查）、Python 编译检查和 Vite 生产构建全部通过。
